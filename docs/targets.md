# Console targets

arisa builds for two consoles. `nx` is the Switch 1: libnx, deko3d and devkitPro's Switch 1 CPU flags (`-march=armv8-a+crc+crypto -mtune=cortex-a57`). `ounce` is the Switch 2: libounce, OunceVK Vulkan, and the SDK's `SWITCH2_CPU` flags (`-mcpu=cortex-a78c+crypto`). Code built for ounce does not run on a Switch 1, and the two targets never share a build directory or a compiler cache.

## Images

Both targets compile with arisa's own toolchain, devkitA64 r30 with GCC 16.1, never with stock devkitA64. `toolchain/Dockerfile` builds `switch-ui-devkita64:r30-gcc16.1`, and `make switch-image` derives `switch-ui-devkita64:r30-gcc16.1-ccache` from it by adding ccache. That image builds nx.

`toolchain/ounce.Dockerfile` builds the ounce image, `switch-ui-devkita64:r30-gcc16.1-ounce20261113`, from the same base. It adds ccache and glslang, checks the SDK archive against its pinned sha256, unpacks it into `/opt/devkitpro` next to libnx without replacing or linking libnx, and builds `toolchain/ounce-smoke`, a C++23 NRO that links libounce and OunceVK's `libvulkan.a`, so a GCC 16 link failure against the prebuilt SDK fails the image build. `make ounce-image` builds it on first use; the SDK archive is read from `OUNCE_SDK_DIR`, which defaults to `~/Documents/projects/sdk-ounce`, through a named build context so the archive never enters the repository.

## Presets and make targets

The `nx` preset uses devkitPro's `Switch.cmake` and builds into `build/nx`. The `switch` preset inherits it and is kept for one release. The `ounce` preset uses libounce's `Switch2.cmake`, which keeps `NINTENDO_SWITCH`, adds `NINTENDO_SWITCH2` and `__SWITCH2__`, puts `portlibs/switch2` first and sets the A78C flags, and builds into `build/ounce`.

`make nx` builds every Switch 1 NRO: conformance, counter, gallery, gpu stage, sample, bench and soak. `make switch` runs the same thing. `make ounce` builds the libraries and the Switch 2 NROs: conformance, counter, gallery, gpu stage, sample, bench and soak. The sample (`examples/sample`, see docs/gpu-content.md) draws with `Deko3dSampleRenderer` on nx and `VulkanSampleRenderer` on ounce; both are compile-only. Since round O4 the Vulkan provider has frame hooks, external textures and NV12 imports, and the gpu stage runs on it with its plasma hook and its RGBA and NV12 video rings drawn by the app into its own `VkImage`s. Since round O5 the ounce gpu stage also has a Decoder mode that plays an H.264 clip from its romfs through libounce's hardware decoder, copied once per frame into linear images that the Vulkan provider samples in place (see docs/gpu-content.md); it is compile-only.

`make package TARGET=switch` writes `arisa-<version>-switch-aarch64.tar.gz` in the nx image, and `make package TARGET=switch2` writes `arisa-<version>-switch2-aarch64.tar.gz` in the ounce image, each with its debug twin and checksums. A switch2 package refuses to load under the Switch 1 toolchain and the switch package refuses the Switch 2 toolchain.

## The Horizon provider on each console

The Horizon provider is one library on both consoles. Everything libnx and libounce share stays in the common sources: input, audio, fonts, surface, lifecycle, system info, haptics, text input, browser, clock, threading and romfs. What differs lives in one console class, chosen at compile time by `__SWITCH2__` in `arisa/provider/horizon/console.hpp` and by `ARISA_HORIZON_CONSOLE` in CMake. `nx::NxConsole` creates the deko3d GPU and keeps the default thread placement. `ounce::OunceConsole` creates the Vulkan GPU (`arisa::provider::vulkan::VulkanGpu`): a Vulkan instance with `VK_KHR_surface` and `VK_NN_vi_surface`, a `VkSurfaceKHR` on the default `NWindow`, a device whose queue can present to it, and a `SwapchainTarget` on that surface. Since round O3 the provider renders the compositor's offscreen passes into render-target textures in the same command buffer as the UI (glass, materials, shared backdrops and the blur chain), fills `GpuTimings` from a timestamp query pool per frame slot read back once that slot's fence has signalled, and binds every buffer and image into a few 16 MiB `vkDeviceMemory` blocks per memory type and tiling, so a gallery run stays far below NVK's 4096 allocations. The vi surface is the only Horizon code in the path; the Vulkan provider itself builds and runs on the host against the system loader, which is how its tests run. Its thread placement is the default table restricted to the core mask the process reports at run time, because the libounce headers document the same cores and priorities as the Switch 1 and nothing more is known about the Switch 2 scheduler. Heap figures come from `mallinfo` on nx and from `heapGetTotalSize` minus `heapGetFreeSize` on ounce, where mimalloc replaces newlib's allocator; the ounce figure is an upper bound because the free count skips space inside partly used pages.

## Resolution on each console

The framebuffer size is a fact of the console class, not of the common surface. `nx::NxConsole::framebuffer` keeps the Switch 1 sizes: 1280x720 handheld and 1920x1080 docked. `ounce::OunceConsole::configure_window` calls `nwindowSetModeDimensions(window, 0, 0, 0, 0)` on the default window when the surface is created, so the Switch 2 renders at the console's own resolution: 1920x1080 handheld, and docked at the TV output setting, 3840x2160 included. `OunceConsole::framebuffer` reads `nwindowGetDimensions`, which libounce updates when `appletMainLoop` handles the operation-mode message and when AM reports a default-resolution change; `HorizonSurface::poll` reports a size change as `resized` (and `scale_changed`) even when the operation mode did not change. `GpuOptions::docked_cap` (unset by default) passes a fixed docked size to `nwindowSetModeDimensions` instead of the TV setting; the system scales that size to the TV, so it caps the docked cost on a 4K TV and is ignored on nx.

The layout root in points does not change between consoles: the pixel scale is `SurfaceScale::for_pixels`, so 1920x1080 is 1.5 and 3840x2160 is 3.0, and the gallery's 1.25 content scale gives the same 1024x576 pt root on a 1280x720 Switch 1 and a 1920x1080 Switch 2. Text, icons, the glyph atlas, shapes, shadows, blur radii and render targets already take the pixel scale (the same path as Switch 1 docked), so a Switch 2 frame is sharper, not bigger.

The swapchain follows the frame. Every frame the UI thread records carries the pixel size it was laid out at (`FramePlan::extent`); the render thread, which presents, passes it to `VulkanTarget::prepare`, and `SwapchainTarget` recreates the swapchain when that size differs from the current one or when the last acquire or present returned `VK_SUBOPTIMAL_KHR` or `VK_ERROR_OUT_OF_DATE_KHR`. A replay frame has no extent and keeps the window's size. The same path resizes an `OffscreenTarget` on the host, which is how it is tested.

Touch keeps the Switch 1 panel space on both consoles. libounce's `hid.h` declares the same `HidTouchState` (`u32 x`, `u32 y`, no range given) inside the same `HidSharedMemory` layout as libnx, with no Switch 2 branch for the touch screen, so touch is read from the compatibility shared memory that Switch 1 software reads in 1280x720. Each console class names its panel (`touch_panel`, a `provider::TouchPanel`), and `HorizonInput` maps it to the framebuffer. This has not been checked on a Switch 2.

## GPU line at startup

Both consoles report the GPU once at startup through the factory's `DiagnosticsProvider`, which the gallery and the other Switch programs point at nxlink: `NxConsole::create_gpu` reports a `arisa.deko3d` line with the swapchain image count, swap interval and texture slots, and `OunceConsole::create_gpu` passes the diagnostics to `VulkanGpu::create`, which reports an `arisa.vulkan` line, `VulkanGpu::startup_report()`, built from `VulkanDevice::report()`: device name, Vulkan API version, driver, upload memory, and the features arisa enabled or detected (rgb565, alpha8 swizzle, portability subset, presentation, synchronization2, timeline semaphores, multi-planar NV12, timestamps). On the host the same line is reported when a diagnostics provider is passed to `VulkanGpu::create`; the Vulkan tests check it on MoltenVK. The ounce line has never been seen on a Switch 2.

## New textures and frame planning

`GpuProvider::create_texture` returns a texture that reads as transparent black until something writes it, on every provider. The rule lives once in `gpu::FramePlanner` (`include/arisa/provider/gpu/frame_planner.hpp`): a partial `update_texture` on a new texture clears it first, a full-rect upload does not; at seal the textures nothing has written yet join the frame, and its plan clears each one before the surfaces, passes and screen, unless its first write in that frame is an offscreen pass that opens with its own clear. A frame that is skipped or abandoned still runs those clears (`FramePlanner::owed`). Vulkan clears with `vkCmdClearColorImage`, deko3d with `clearColor` on the texture bound as the render target (every deko3d texture is created with `DkImageFlags_UsageRender`; all five formats it uses can render), and the headless GPU fills its canvas.

The same plan carries the rules the backends used to repeat: damage accumulated per swapchain image, offscreen passes with an empty region or a missing target skipped, underlay holes mapped through the pass region or clipped to the screen damage, and the screen scissor when only part of the image is repainted. Deko3d, Vulkan and the headless GPU each walk the steps with their own native calls. The SDL3 GPU does not use the planner yet and does not clear new textures.
